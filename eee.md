# Командный проект ТП: карта дорожных дефектов

Краудсорсинговый сервис: пользователи отмечают на карте дорожные дефекты (яма, провал, стёртая разметка, нерабочий знак) с фото и координатой. Сервис склеивает дубликаты соседних сообщений в один объект, показывает тепловую карту и ведёт статус объекта от заявки до устранения.

Команда: 4 человека.

## Почему эта тема

Из 25 прошлогодних проектов ни одного геосервиса — темы повторяются (два финансовых трекера, два рецептурных сервиса, маркетплейсы и трекеры). Карта даёт визуально отличимую защиту.

При этом ядро остаётся обычным CRUD: регистрация, роли, сущности, поиск, статусы. Сложность сосредоточена в одном месте — пространственной обработке, — и это место изолировано в отдельном сервисе, то есть не блокирует остальную команду.

Чек-лист оценивания закрывается без натяжки: роли (житель / модератор / служба), поиск (по адресу, категории, статусу, радиусу), чат (обсуждение под каждым объектом), мобильный адаптив (заявку подают с телефона на месте).

## Архитектура

```
браузер ──REST/JSON──> Go API ──gRPC──> C++ worker
  (nginx: статика       (auth, CRUD,     (склейка дубликатов,
   + reverse proxy)      PostGIS)         тайлы, heatmap)
```

На двух границах — разные протоколы, у каждого своя причина.

**Браузер ↔ Go — REST + OpenAPI.** Это то, что идёт в Swagger и в рубрику.

**Go ↔ C++ — gRPC.** Один `.proto` порождает обе стороны: `protoc-gen-go-grpc` для Go, `userver_add_grpc_library` (или обычный `grpc_cpp_plugin`) для C++. Контракт между сервисами не пишется руками и потому не расходится с кодом. Микросервисная архитектура подтверждается протофайлом, а не словами в презентации.

## Стек

### Go API

| Что | Чем |
|---|---|
| Роутер | Gin |
| Swagger | `swaggo/swag` + `gin-swagger`, UI на `/swagger/index.html` |
| БД | PostgreSQL + PostGIS, доступ через `pgx` + `sqlc` |
| Миграции | `goose` |
| Auth | `golang-jwt/jwt/v5`, подтверждение почты одноразовым токеном |
| Почта | `go-mail`, в dev — MailHog в compose |
| Логи | stdlib `log/slog` в JSON + middleware с request-id |
| Тесты | `testing` + `testify`, интеграционные через `testcontainers-go` с PostGIS |

**Не ORM.** Гео-запросы (`ST_DWithin`, `ST_ClusterDBSCAN`, `ST_AsMVT`) пишутся на SQL руками; GORM здесь только мешает, а sqlc из того же SQL сгенерирует типизированные Go-функции.

**Альтернатива по Swagger:** `oapi-codegen` вместо swaggo, если хочется, чтобы спека была источником истины — не реализовал метод, не скомпилировалось. Ценой ручного встраивания UI.

### C++ worker

Задача сервиса: принял набор точек — вернул кластеры, тайл или тепловую карту.

**Рекомендуемый вариант — голый `grpc++` + Eigen + nanoflann.** Собирается быстро, зависимостей минимум, вся ценность (пространственный индекс, DBSCAN) на месте.

**Вариант с userver** — если нужны его корутины, конфиги, метрики и testsuite. Тогда обязательно собирать на официальных базовых образах из `scripts/docker/` репозитория userver (`ubuntu-24.04-userver.dockerfile`, `ubuntu_install_grpc.sh`), иначе команда потеряет неделю на установку зависимостей.

Отдельно про Swagger в userver: автоматической генерации спеки из кода там нет. Есть `chaotic` (JSON Schema → C++ типы) и `chaotic-openapi` (OpenAPI 3.x / Swagger 2.0 → C++ HTTP **клиент**, не сервер). Публичный REST в этом проекте отдаёт Go, поэтому вопрос не возникает.

### Фронтенд

Чистый HTML + JS (ES-модули, без сборщика) + Leaflet + Leaflet.markercluster. Карта-библиотеки изначально vanilla, поэтому отказ от React здесь ничего не стоит, а Docker-образ фронта сводится к nginx со статикой.

Два места, которые надо спланировать заранее, иначе всплывут в последнюю неделю:

**i18n.** Библиотека не нужна: `i18n/ru.json` и `i18n/en.json`, разметка `<span data-i18n="report.status.fixed">`, одна функция `applyI18n(dict)`, проходящая по `[data-i18n]`. Язык в `localStorage` и он же в заголовке `Accept-Language`, чтобы бэкенд локализовал ошибки валидации. Правило с первого дня: никакого русского текста прямо в HTML, только ключи.

**Логирование.** Обёртка над `console`, дублирующая warn/error POST-ом на `/api/logs`, плюс `window.onerror`.

Адаптив — CSS grid/flex и media queries; при желании Pico.css или Bootstrap по CDN (это не JS-фреймворк, стек не ломает). Валидация — HTML5 Constraint Validation API (`required`, `pattern`, `setCustomValidity`) плюс те же правила на бэкенде. Тесты — `node:test` для модулей, `Playwright` на два-три e2e-сценария.

## Схема данных

| Таблица | Ключевые поля |
|---|---|
| `users` | id, email, password_hash, role, email_verified, locale, created_at |
| `email_tokens` | token, user_id, expires_at, used_at |
| `reports` | id, author_id, cluster_id, category, description, photo_url, geom (POINT, 4326), created_at |
| `clusters` | id, geom, category, status, reports_count, confirmed_at, fixed_at |
| `status_history` | id, cluster_id, from_status, to_status, actor_id, at |
| `messages` | id, cluster_id, author_id, body, created_at |

Роли: `citizen` (создаёт заявки, комментирует), `moderator` (подтверждает, объединяет, скрывает спам), `service` (представитель службы: берёт в работу, закрывает), `admin`.

Статусы кластера: `reported → confirmed → in_progress → fixed`, плюс `rejected`.

Индексы: GiST по `reports.geom` и `clusters.geom` — без них поиск по bbox деградирует сразу.

## Эндпоинты

**Аутентификация**
- `POST /api/auth/register` — регистрация, отправка письма
- `GET /api/auth/verify?token=` — подтверждение почты
- `POST /api/auth/login`, `POST /api/auth/refresh`
- `GET /api/me`

**Заявки и объекты**
- `POST /api/reports` — multipart: фото + координата + категория
- `GET /api/reports?bbox=&category=&status=&q=` — поиск
- `GET /api/clusters?bbox=&zoom=` — объекты для карты
- `GET /api/clusters/{id}` — карточка с историей статусов
- `PATCH /api/clusters/{id}/status` — смена статуса (moderator / service)

**Карта**
- `GET /api/tiles/{z}/{x}/{y}.mvt` — векторные тайлы
- `GET /api/heatmap?bbox=` — тепловая карта

**Прочее**
- `WS /api/clusters/{id}/chat` — обсуждение объекта
- `POST /api/logs` — приём фронтовых логов
- `GET /swagger/index.html` — Swagger UI

**gRPC (`worker.proto`)**
- `ClusterReports(ClusterRequest) returns (ClusterResponse)`
- `BuildTile(TileRequest) returns (TileResponse)`
- `Heatmap(HeatmapRequest) returns (HeatmapResponse)`

|---|---|
| Swagger | `swaggo/swag` + `gin-swagger`, UI поднимается сам |

## docker-compose

Пять сервисов: `postgis`, `go-api`, `cpp-worker`, `nginx` (статика фронта и прокси на `/api`), `mailhog`. Один `docker compose up` закрывает пункты «Docker» и «удалённая работа» сразу.

## План по спринтам

**Спринт 1 — скелет.** Auth с подтверждением почты, CRUD заявок, карта с точками, docker-compose, CI с линтерами, Swagger. К концу спринта продукт целиком работает, пусть и примитивно.

**Спринт 2 — продукт.** Роли и переходы статусов, поиск, чат, склейка дубликатов **наивно на Go** прямо в API, Figma-макеты и адаптив.

**Спринт 3 — глубина.** C++ worker за gRPC-интерфейсом вместо наивной реализации, векторные тайлы и heatmap, i18n, тесты, логирование.

**Спринт 4 — сдача.** Руководство пользователя, документация, README, видео, e2e-сценарии, полировка.

## Роли

1. **Go: домен** — сущности, sqlc, миграции, гео-поиск, Swagger-аннотации
2. **Go: платформа** — JWT, почта, middleware и логи, чат на WebSocket, CI, compose
3. **Фронтенд целиком** — Figma → HTML/JS, Leaflet, адаптив, i18n, валидация, фронтовые логи и тесты
4. **C++ worker и контракт** — `.proto`, обе стороны gRPC, DBSCAN и kd-tree, тайлы; он же держит e2e-тесты

## Риски

**C++ сервис на критическом пути.** Снимается порядком спринтов: во втором спринте склейка дубликатов работает наивно на Go, в третьем за тем же gRPC-интерфейсом появляется C++. Если он не взлетит — теряются баллы за доп. фичи, но не проект.

**Сборка userver.** Если всё же выбран userver — только официальные базовые образы, иначе неделя уходит на «у меня не собирается» вместо i18n и тестов. Лучший вариант: не брать userver для вычислительного воркера, взять голый `grpc++`.

**Расхождение спеки и кода.** Аннотации swaggo живут рядом с хендлерами, но всё равно нужен CI-шаг, который прогоняет `swag init` и падает, если сгенерированная спека отличается от закоммиченной.

**Тексты в HTML.** Локализация постфактум мучительна. Ключи вместо текста — с первого коммита.
